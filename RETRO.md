# Retro log

Learnings from sessions, one line each. Appended as they happen, reviewed on demand with the `toolkit` skill, and deleted once acted on.

A line belongs here when it is: something inefficient a toolkit change would fix, a pattern that works better than what we currently tell agents to do, or a repetition worth a new skill or plugin. Not bugs, not project notes.

Format: `- YYYY-MM-DD · <agent> · <project> — <what was inefficient, and what would be better>`

- 2026-08-14 · developer · unyt-workshop — mutation testing (mutate the production code, re-run the harness, record which assertions stay green) found four unfalsifiable assertions that three read-only review passes had missed or under-rated. Worth naming as a technique in the reviewer and developer definitions rather than being reinvented per session.
- 2026-08-15 · developer · unyt-workshop — bash 3.2 ends a `$( )` by scanning for the closing paren rather than parsing, so a `)` inside a case pattern or a comment truncates the substitution; `bash -n` cannot see it and the error surfaces at an innocent line. Any shell script that runs on a macOS runner should be checked with `docker run bash:3.2` in the local loop — two CI round trips went to this.
- 2026-08-17 · gallery-shooter · unyt-workshop — curating a screenshot gallery by eye conflates "content changed" with "timestamp changed"; reach for a pixel-diff bounding box first when a fixture carries a Date.now(), so only real deltas get committed.
- 2026-08-18 · developer · unyt-workshop — ran the full hour-long sweettest suite three times mid-loop (killing two) because the definition says to reproduce the shape CI runs, without saying that applies to the final verification rather than every iteration. The developer definition should say: iterate against the specific test, run the full gate set once before handing back.
- 2026-08-18 · architect · unyt-workshop — specced a defensive check, had it settled and reopened twice, because an existing guarantee elsewhere (disallow_rated_and_nameable_units) already rejected the same input class and nothing surfaced it. Before specifying a new check, grep for what already rejects that input and state the answer in the spec even when it is "nothing" — that line would have short-circuited three rounds.
- 2026-08-18 · developer · unyt-workshop — isolation: worktree hands a superproject worktree with no submodules checked out, and the guard refuses `git -C`/`--git-dir` against the shared checkout, so a repo living in a submodule is unreachable and the first ten minutes go on inventing a local-clone workaround. The toolkit should say what to do when the assigned worktree does not contain the repo the brief names.
- 2026-08-19 · developer · unyt-workshop — `make test` depends on `build` so sweettests never run against a stale happ; invoking `cargo test -p sweettest` directly to filter one case bypasses that silently, costing a 7-minute run and a false alarm. A filtered test run must still satisfy the suite's build dependency.
- 2026-08-19 · developer · unyt-workshop — cargo's `--config` is not forwarded to external subcommands, so `cargo --config 'patch.crates-io...' clippy` silently ignores the patch while `build`/`test` honour it. Verifying against an unpublished dep needs a temporary `.cargo/config.toml`, plus an explicit `git status` and lockfile check before committing.
- 2026-08-19 · developer · unyt-workshop — self-review caught nothing on new assertions, but the reviewers' "can this pass while the behaviour is wrong?" caught a real hole. The developer's self-review step should name mutation as the check for any test whose assertions are relative rather than exact.
